# Contriboost Smart Contract Audit

**Scope:** `src/contriboost.sol`, `src/contriboostFactory.sol`, `src/goalFund.sol`, `src/goalFundFactory.sol`
**Date:** 2026-07-24
**Method:** Manual line-by-line review. No fuzzing/formal verification performed — treat this as a first-pass review, not a substitute for a professional third-party audit before mainnet deployment with real funds.

Severity scale: **Critical** (loss/lockup of funds, or full bypass of access control) · **High** (funds at risk under realistic conditions) · **Medium** (breaks an invariant / griefing) · **Low** (best-practice, unlikely to be exploited) · **Info** (style/gas).

---

## Critical

### C-1. `Contriboost` owner is the Factory contract, not the host — all `onlyOwner` functions are permanently unreachable
**File:** `contriboost.sol:9,74` + `contriboostFactory.sol:42-48`

`Contriboost` inherits `Ownable` and calls the base `Ownable()` constructor with no arguments. OpenZeppelin's `Ownable` constructor sets `_owner = msg.sender` at construction time. Every `Contriboost` is deployed via `new Contriboost(...)` **inside `ContriboostFactory.createContriboost`**, so `msg.sender` at that point is the **factory's address**, not the host who called `createContriboost`. Compare with `GoalFund`, which correctly calls `_transferOwnership(_host)` in its constructor (`goalFund.sol:91`).

Because `ContriboostFactory` never exposes a passthrough to call functions on the child contracts, the following are **permanently locked and can never be called by anyone**:
- `setTokenAddress` (contriboost.sol:133)
- `setHostFeePercentage` (contriboost.sol:141)
- `setDescription` (contriboost.sol:146)
- `emergencyWithdraw` (contriboost.sol:331) — **the only fund-recovery mechanism in the contract**

**Impact:** if funds ever get stuck (see C-2), there is no path to recover them — not even for the host or the platform owner. This silently defeats the entire purpose of `emergencyWithdraw`.

**Fix:** in the constructor, call `_transferOwnership(host)` (i.e. `msg.sender` of `createContriboost`, threaded through as a constructor arg — same pattern `GoalFund` already uses), or have the factory pass `tx.origin`/an explicit host param and transfer ownership to it after construction.

### C-2. `join()` allows unlimited participants after `startTimestamp`, permanently bricking `distributeFunds`
**File:** `contriboost.sol:116-121` (`canJoin`) and `contriboost.sol:232-233` (`distributeFunds`)

```solidity
modifier canJoin() {
    require(msg.sender != address(0), "Invalid participant address");
    require(!participants[msg.sender].exists, "You are already a participant");
    require(participantList.length < expectedNumber || block.timestamp >= startTimestamp, "...");
    _;
}
```

This is a logical-OR where the intent was clearly an AND-of-negations guard ("reject only if full AND not started"). Read the truth table: once `block.timestamp >= startTimestamp`, the require **always passes**, regardless of `participantList.length`. So **any number of extra addresses can join after the cycle starts**, with no upper bound.

`distributeFunds` requires exact equality: `require(participantList.length == expectedNumber, ...)`. Once a single extra participant joins post-start, `participantList.length` permanently exceeds `expectedNumber` and can never come back down (no leave function) — `distributeFunds` reverts forever.

**Impact:** combined with C-1 (no working `emergencyWithdraw`), every deposit already collected in the contract becomes **permanently stuck with no recovery path**. This requires no privileged access to trigger — any wallet calling `join()` after start time bricks the pool for everyone.

**Fix:** the condition should be `participantList.length < expectedNumber && block.timestamp < startTimestamp_or_whatever_join_window_is` — i.e. cap participants strictly at `expectedNumber` regardless of timing. Re-derive the intended join window and use `&&`, not `||`. Also consider `depositAllowed` (line 125), which has the same `>=` vs `==` looseness (`participantList.length >= expectedNumber`) — harmless today only because it's downstream of the same bug.

## High

### H-1. `GoalFund.getTokenContribution()` ignores the caller's intended amount and pulls `min(allowance, balance)`
**File:** `goalFund.sol:136-144`

```solidity
function getTokenContribution() internal returns (uint) {
    uint allowance = token.allowance(msg.sender, address(this));
    uint balance = token.balanceOf(msg.sender);
    uint amount = allowance < balance ? allowance : balance;
    require(amount > 0, "No tokens approved or available");
    bool success = token.transferFrom(msg.sender, address(this), amount);
    ...
}
```

`contribute()` for the ERC20 path takes **no amount parameter at all** — it pulls whatever is approved, capped by the caller's full wallet balance. Many wallets/dapps set `approve(spender, type(uint256).max)` once for UX convenience (a very common pattern). If a user has done that for this token anywhere, calling `contribute()` here pulls **their entire token balance**, not the amount they meant to contribute. There is no way to make a partial/bounded contribution via this function.

**Impact:** silent, one-shot draining of a user's full token balance into the fund on a single `contribute()` call, if they've ever granted a large/unlimited allowance. This is a real fund-safety issue, not just a UX rough edge.

**Fix:** add an explicit `uint256 amount` parameter to `contribute()`/`getTokenContribution()` and `transferFrom` exactly that amount (`require(amount > 0)`, no min-with-balance logic).

### H-2. Plain `IERC20.transfer`/`transferFrom` return values trusted without `SafeERC20`
**Files:** `contriboost.sol:182,218,250,260,273,343`, `goalFund.sol:141,193`, `contriboostFactory.sol:148`, `goalFundFactory.sol:167`

All four contracts call `token.transfer(...)` / `token.transferFrom(...)` directly and check the returned `bool`. Tokens that don't strictly follow EIP-20 (e.g. USDT on mainnet, and various others) either don't return a bool at all (call reverts due to decoding failure — that direction is actually safe-ish) or worse, some non-standard tokens return `true` unconditionally regardless of actual outcome. The project already vendors OpenZeppelin, which ships `SafeERC20` (`token/ERC20/utils/SafeERC20.sol`) precisely for this — it isn't used anywhere.

**Fix:** use `SafeERC20.safeTransfer` / `safeTransferFrom` throughout instead of raw `IERC20` calls.

## Medium

### M-1. No fee-on-transfer / deflationary-token handling
**Files:** `contriboost.sol:182` (`deposit`), `goalFund.sol:109-122` (`_contribute`)

`contriboost.sol` credits `participant.depositAmount += contributionAmount` (the *requested* amount) rather than the amount actually received. If the configured ERC20 ever charges a transfer fee (deflationary/rebasing tokens), the contract's internal accounting (and `token.balanceOf(address(this))` used later in `distributeFunds`) will disagree with what participants are credited for, and `distributeFunds` will eventually run out of real balance to pay out the last recipients. Same class of issue applies conceptually to `GoalFund`, though it's naturally less exposed since it swept the whole approved amount (see H-1).

**Fix:** measure `balanceBefore`/`balanceAfter` around `transferFrom` and credit the delta, or explicitly document/enforce that only standard, non-fee tokens may be configured (and validate that at `setTokenAddress`/token-selection time).

### M-2. `distributeFunds` recipient is chosen by join order, without requiring the recipient to have deposited this cycle, and payout isn't gated on this segment's expected inflows
**File:** `contriboost.sol:232-285`

`distributeFunds` can be called by the host at any time (subject only to `participantList.length == expectedNumber`), and pays out `recipient = participantList[currentSegment - 1]` from whatever the **current total contract balance** happens to be — there's no check that all (or any) participants actually deposited for `currentSegment` before the host distributes. `checkMissedDeposits()` is invoked but only flags/deactivates chronically-missing participants; it doesn't block distribution. A host could call `distributeFunds` immediately after contract deployment/funding with a tiny leftover balance and pay it to segment 1's recipient before others have contributed anything for that round.

This may be partially intentional for a ROSCA-style host-controlled cadence, but as written the host has near-total discretion over *when* and *from what pool size* each recipient gets paid, which participants are trusting the host not to abuse. Worth confirming this matches the intended trust model, and documenting it clearly for users (who might assume payout is strictly "this round's contributions only").

### M-3. `receivedFunds` is written but never checked
**File:** `contriboost.sol:277`

`participants[recipient].receivedFunds = true` is set but nothing gates future payouts on it. Combined with M-2, if `distributeFunds` is called extra times within a cycle (e.g., due to timing quirks around the segment-reset logic at lines 280-284), the same recipient could conceivably be paid again before `currentSegment` correctly advances past them. Recommend using `receivedFunds` (or an explicit per-segment paid map) as a hard guard: `require(!participants[recipient].receivedFunds || <new cycle>, ...)`.

### M-4. Unbounded loop over `participantList` in `checkMissedDeposits`
**File:** `contriboost.sol:195-209`

Called from `distributeFunds` (and publicly). Gas cost grows linearly with `expectedNumber`/participant count. For the intended use case (small savings circles) this is likely fine, but there's no explicit cap on `expectedNumber` anywhere in the contract or factory — a large group could make `distributeFunds` (and therefore every payout) unaffordable or hit the block gas limit.

**Fix:** enforce a sane upper bound on `expectedNumber` in the constructor/factory, or move missed-deposit accounting off-chain / to a pull-based per-participant check.

## Low / Informational

- **`SafeMath` on Solidity `^0.8.19`** (`contriboost.sol:10`, `goalFund.sol:10`): Solidity ≥0.8 has built-in overflow/underflow checks; `SafeMath` here is dead weight (extra gas, no added safety). Safe to remove and use plain `+`/`-`/`*`/`/`.
- **`ContriboostFactory`/`GoalFundFactory` `emergencyWithdraw`** (`contriboostFactory.sol:138`, `goalFundFactory.sol:157`): these are correctly gated (factory's own `owner()` is the actual deployer), but note they only rescue tokens/ETH sent directly to the *factory*, not to individual child contracts — which is consistent with, but doesn't fix, C-1.
- **`hostFeePercentage` mutable mid-cycle** (`contriboost.sol:141-144`, currently unreachable per C-1): once C-1 is fixed and the host can call this, consider locking the fee once `participantList.length > 0` so a host can't raise fees on participants who already joined expecting a lower rate.
- **No re-entrancy risk found** in fee/payout ordering (checks-effects-interactions is mostly followed, and `nonReentrant` is applied consistently) — this is one of the stronger aspects of the current code.
- **Zero-address checks** are present for the important constructor params (`_platformOwner`, `_beneficiary`) — good.
- Consider adding NatSpec (`@notice`/`@param`) across all public/external functions for downstream integrators and easier verification tooling.

---

## Suggested remediation order

1. Fix **C-1** (ownership wiring) and **C-2** (join overflow) together — they compound into unrecoverable fund lockup and are both one-line-scope fixes.
2. Fix **H-1** (bounded `contribute(amount)`).
3. Adopt **H-2** (`SafeERC20`) repo-wide.
4. Revisit **M-1**–**M-4** depending on whether fee-on-transfer tokens and large groups are in scope for this deployment.

None of the Critical/High items are fixed in this pass — they require an on-chain redeploy of `Contriboost`/`GoalFund` (or a new factory version) rather than a config change, so flagging them here for your decision before doing the rewrite.
